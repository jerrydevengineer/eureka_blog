# Join(INNER, OUTER, SELF, CROSS)

## 관계 대수(SQL 조인)

관계형 데이터베이스는 데이터 중복을 방지하기 위해 데이터를 여러 개의 분산된 테이블에 저장합니다. 조인은 이런 데이터들을 다시 결합하여 실제 비즈니스에 사용하기 위해 사용됩니다.

### INNER JOIN(정확한 매치)

이너 조인은 두 테이블에서 정확히 일치하는 로우들만 반환합니다. 만약 A 테이블에 있는 값이 B 테이블에 없다면 결과에 반환 되지 않습니다.

시나리오: 실제로 주문을 한 고객의 디테일을 보고 싶습니다.

```sql
SELECT c.name, c.email, o.order_date, o.status
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id;
```

- DB는 우선 customers 테이블을 보고 customer_id를 가져옵니다. 그리고 orders 테이블을 보고 매치가 되는 행이 있으면 두 테이블에서 데이터를 가져와서 보여줍니다.

### OUTER JOIN(없어도 반환)

가끔은 다른 테이블에 매치 되는 데이터가 없더라도 테이블의 모든 데이터가 필요한 경우가 있습니다. 이때 LEFT JOIN과 RIGHT JOIN을 사용합니다.

시나리오: 모든 고객을 보고 싶고, 주문을 한 적이 있으면 주문 일자를, 없으면 빈 칸으로 보고 싶습니다.

```sql
SELECT c.name, o.order_id, o.order_date
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id;
```

- 왜 LEFT인가요? 결과 테이블은 왼쪽에 있는 값을 우선 반환합니다. 오른쪽에 매치되지 않는 행이 있더라도 그냥 그 값을 NULL로 둡니다.(RIGHT JOIN 또한 정확하게 같은 일을 합니다. 하지만 업계 표준은 LEFT JOIN을 사용합니다.)


### SELF JOIN

SELF JOIN은 말 그대로 같은 테이블과 조인하는 것입니다. 하나의 테이블을 alias를 사용하여 두 개의 다른 테이블처럼 취급합니다.

시나리오: 고객 중에 같은 주소에 사는 고객들을 찾고 싶습니다.

```sql
SELECT c1.name AS Person1, c2.name AS Person2, c1.address
FROM customers c1
JOIN customers c2 ON c1.address = c2.address 
                 AND c1.customer_id != c2.customer_id;
```

- 같은 테이블에서 두 행이 같은 주소에 살지만 id가 다른 경우를 반환합니다.


## CROSS JOIN

CROSS JOIN은 모든 조합을 찾는 방법입니다. ON 절로 조건을 주지 않고, 한 테이블의 한 행에 다른 테이블의 모든 행을 붙여서 반환합니다.

시나리오: 모든 고객과 모든 상품의 조합을 보고 싶습니다.

```sql
SELECT c.name, p.name 
FROM customers c CROSS JOIN products p;
```

- 주의할 점: 만약 1,000,000 고객과 100,000 상품이 있다면, 결과는 1000억 행이 될 것입니다. 이렇게 되면 1000억 행만큼의 RAM이 필요하게 되고 한 행의 컬럼 및 데이터가 많을 경우 OOM이 일어납니다. 물론 실무에서 CROSS JOIN을 사용할 일은 거의 없지만, 테스트 데이터 셋 등을 만들 때 발생할 수 있습니다.


# JOIN이 실행되는 과정

JOIN은 단순히 실행되지 않습니다. 쿼리가 실행되기 전에 정교한 과정을 거쳐 빠르게 쿼리를 실행할 수 있는 방법을 찾습니다.

## Optimizer And Execution Plan

쿼리가 데이터를 찾기 전에 쿼리문은 우선 파싱 돼서 쿼리 옵티마이저로 갑니다. 옵티마이저는 테이블 메타 데이터를 보고 여러 가지 쿼리 실행 플랜의 코스트를 계산합니다. 이것은 어떤 테이블을 먼저 읽을지, 조인을 위한 어떤 알고리즘을 사용할 지, 인덱스를 사용할 지 풀 스캔을 할 것 인지를 판단합니다. 결정이 완료되면 플랜을 엔진에게 넘겨줍니다.


## Join Algorithms

### 1. loop join(기본 조인)

java에서 두 개의 for 문을 사용하는 것과 정확히 같습니다.

``` Java
for (Row customer : customersTable) { // Outer Loop
    for (Row order : ordersTable) {   // Inner Loop
        if (customer.id == order.customer_id) {
            results.add(join(customer, order));
        }
    }
}
```

- 데이터베이스는 outer table에서 한 행을 읽습니다. 그리고 그 다음에 inner table에서 모든 데이터를 읽고 매치 되는 행을 찾습니다. 이 과정을 모든 outer table의 행에 대해서 반복합니다.


### 2. index loop join

B-Tree Index를 사용해서 최적화된 loop join입니다.

index는 분리되고 정돈된 탐색 트리입니다. index가 join에 활용되는 컬럼에 있을 때, db는 내부 for문을 건너 뛸 수 있습니다.

- 우선 outer table의 행을 읽습니다. 그리고 inner table의 모든 행을 읽지 않고, index를 활용해 inner table의 해당 키의 위치를 검색하고 반환할 수 있습니다$O(logN)$.


### 3. hash join

*MySQL은 8.0부터 Hash Joins를 지원하기 시작했습니다.*

인덱스가 없거나 데이터베이스가 두 테이블의 상당 부분을 조인해야 한다는 것을 알고 있는 경우, B-트리를 수백만 번 스캔하는 것은 실제로 메모리에서 처리하는 것보다 느려질 수 있습니다.

- Build: db는 두 테이블 중 작은 테이블을 메모리에 올리고 join에 활용되는 컬럼을 키로 가지는 Hash Map을 만듭니다.
- Probe: db는 더 큰 테이블을 한 행씩 확인하면서 join에 활용되는 컬럼을 해싱하고 메모리에 있는 Hash Map에서 검색합니다.
- 주의사항: Hash Map은 메모리에 올라갑니다. 메모리가 부족할 경우, hash map의 일부를 하드나 ssd에 저장해야 되므로 성능이 매우 떨어질 수 있습니다.

## Disk I/O vs. Memory

알고리즘이 진행될 때 db는 물리 디스크에 있는 데이터를 Buffer Pool이라고 불리는 메모리에 담습니다.

쿼리가 버퍼 풀보다 큰 테이블을 스캔해야 하는 경우, 데이터베이스는 디스크에서 읽어오는 새 데이터를 위한 공간을 확보하기 위해 RAM에서 오래된 데이터를 지속적으로 제거해야 합니다. 메모리 용량이 엄격하게 제한된 경우 잘못된 쿼리가 즉시 드러나는 이유가 바로 이것입니다. 디스크는 RAM 부족을 보완하기 위해 엄청난 노력을 기울여야 합니다.


### 팁: 확인하는 법

`EXPLAIN SELECT * FROM orders o JOIN customers c ON o.customer_id = c.customer_id;`

MySQL은 어떤 알고리즘을 사용했는지, 어떤 테이블이 "외부" 테이블인지, 그리고 인덱스를 사용할지 아니면 전체 테이블 스캔을 수행할지 등을 표로 보여줍니다.



# Query Optimizer

query optimizer는 코스트 기반 최적화를 진행합니다.

## Parser(Syntax and Semantics)

옵티마이저가 작업 전에 db가 먼저 쿼리를 이해해야 합니다.

1. 어휘/구문 검사: 맞춤법, 문법 오류 등을 검사합니다.
2. 의미론적 확인: 테이블 및 컬럼이 실제로 잇는지, 유저의 권한이 있는지 등 검사합니다.
3. 검사가 완료되면 Parse Tree라는 형태로 SQL이 변환됩니다.

## Statistics Engine

옵티마이저는 플랜을 정하기 위해 실제 데이터를 보지 않습니다. 대신 통계를 보고 결정합니다. db는 항상 백그라운드 작업으로 테이블에 대한 메타데이터를 관리합니다.

- 테이블 크기: 테이블에 얼마나 많은 행이 있는지, 하드 드라이브에서 얼마나 큰 블록을 차지하는지
- 인덱스 카디널리티: 컬럼에 얼마나 많은 유니크 밸류가 있는지 확인합니다(카디널리티(cardinality)는 상대적입니다. 성별이여도 국가의 값이 1개라면 성별이 차수가 더 높을 수도 있음).

## Cost Calculation

옵티마이저는 Parse Tree를 보고 여러 개의 가능한 플랜을 만듭니다. 그리고 각 플랜의 코스트를 계산합니다. 코스트는 주로 Disk 접근과 CPU 사용량으로 계산됩니다. 이 중에서 실제 disk 접근이 가장 오래 걸리기 때문에 이를 최소화하는 방향으로 갑니다.

대표적으로 Index 기반 탐색과 풀 스캔을 비교해보겠습니다.

Index를 활용하는게 항상 좋을까요? 인덱스를 활용한 접근은 랜덤한 접근입니다. 이 뜻은 디스크의 다른 부분으로 이동해야 한다는 말입니다. 하지만 풀 스캔은 순차적 접근을 합니다. 디스크의 블록을 연속적으로 읽어서 빠르게 가져올 수 있습니다.

예를 들어 100만 개의 데이터가 있는 고객 테이블에서 1명의 고객 데이터만 가져올 때는 index를 활용하는 것이 압도적으로 빠릅니다. 하지만 80%의 고객 데이터를 가져오고 싶다면 80만 번의 인덱스를 타야한다는 말이고(물론 B+Tree 특성 상 한 행의 데이터 양이 작아서 한 블록에서 근접 행들의 데이터를 가져와서 줄어들 수 있습니다.) 이는 풀 스캔보다 오래 걸리고 옵티마이저는 풀 스캔을 선택합니다.

추가: B+Tree는 리프노드에만 데이터가 있고 양 쪽으로 연결된 리스트 구조를 사용합니다. db는 기본적으로 PK로 만들어진 index에만 데이터를 담아놓고(이게 그냥 기준 테이블입니다), 다른 컬럼으로 index를 만들면 데이터로 pk만 담고 있습니다. 즉 만약 나이를 기준으로 age > 20 같은 조건을 자주 넣는다면 index를 만들어도 쓸모가 없다는 뜻이죠!(데이터가 많을 수록 해당 테이블에서 작은 퍼센테이지여도 풀스캔 일어남). age > 20으로 가져온 데이터가 pk 뿐이므로 이 pk를 활용해서 또 데이터를 가지러 가야함. 이 때는 어떻게 해야할까요. 그냥 풀스캔을 하도록 냅두고 age index를 삭제하거나, 커버링 인덱스를 사용해야합니다. 하지만 커버링 인덱스도 age를 기준으로 소량의 컬럼만 추출할 때 사용하는 게 좋습니다. 모든 건 트레이드 오프 계산해봐야죠.

최소의 코스트를 찾으면 엔진(mysql의 InnoDB)에게 플랜을 넘겨주고 엔진에서 하드에 접근해서 메모리에 올려줍니다.

# 좋은 API 설계란?

좋은 api란 예측 가능하고, 안전하며 시스템 리소스를 고려합니다.


## Resource-Oriented Naming (REST Principles)

좋은 api는 명사로 리소스를 구분할 수 있고 동사로 HTTP methods를 사용하는 겁니다.

* **Bad:** `GET /getCustomerById?id=5` or `POST /updateCustomerAddress`
* **Good:** `GET /customers/5` (Retrieves customer 5) or `PUT /customers/5/address` (Updates the address of customer 5)

이렇게 하면 프론트 개발자들이 문서를 읽지 않고도 직관적으로 endpoint를 찾을 수 있습니다.


## Meaningful HTTP Status Codes

어플리케이션이 자바 에러를 뱉는다면, 스프링이 자동으로 500 Internal Server Error를 보여줍니다. 이처럼 좋은 API는 에러를 캐치하고 의미있는 HTTP 코드로 변환해줍니다.

* **200 OK:** 성공
* **201 Created:** 새로운 리소스가 성공적으로 저장됨
* **400 Bad Request:** 잘못된 url 또는 적합하지 않은 데이터 입력
* **404 Not Found:** 리소스를 찾지 못함 `GET /customers/9999999` -> 해당 키를 가진 고객 없음
* **500 Internal Server Error:** 서버에서 에러가 터졌을 때

## Strict Boundary Control (DTOs)

좋은 api는 절대 entity를 노출하지 않습니다. 각 api에 사용되는 DTO를 만들어서 반환해야합니다. 예를 들어 `GET /customers/1`이 고객 정보 확인일 때, 보여줘서는 안되는 비번이나 상태(보여줘야하면 반환해야하지만) 등을 보내면 안됩니다. 또한 여기서 naming_convention이 혼용 되는 경우 바꿔줍니다(db는 주로 snake_case, javascript는 주로 camelCase).


## Pagination and Resource Limits

좋은 api는 과부하를 방지합니다. 만약 단순히 `GET /orders`를 호출한다면, 테이블의 모든 데이터를 가져와서 서버의 메모리를 순식간에 전부 차지할 수 있습니다. 또한 이 데이터를 전부 반환하는데 네트워크 대역폭도 많이 차지합니다.

견고한 api를 위해서는 페이지네이션이 필수적입니다.
`GET /orders?page=1&size=50` 같은 api는 sql query에 적당한 양만큼을 설정해주고 서버와 db, 네트워크 리소스들을 덜 사용하게 해줍니다.
