Architecture

Java Swing UI와 DAO 기반 DB 접근을 분리한 구조

UI Layer

LoginFrame, MainFrame, AdminFrame, Dialog, Panel로 사용자·관리자 화면을 구성했습니다.

DAO Layer

UserDAO, AccountDAO, TransactionDAO, PromotionDAO가 SQL 실행과 ResultSet 매핑을 담당합니다.

Model Layer

User, Account, Transaction, Promotion 객체로 화면과 DB 사이의 데이터를 전달합니다.

Database

MySQL과 JDBC Connector를 사용하고, 송금·취소 같은 핵심 작업은 트랜잭션으로 처리합니다.

ERD

계좌를 중심으로 회원, 은행, 상품, 거래가 연결됩니다.

users 회원

  • PK user_id
  • login_id, password
  • name, email, phone_number
  • role, status

accounts 계좌

  • PK account_id
  • FK user_id, bank_id
  • FK promotions_id
  • account_number, balance, is_active

transactions 거래

  • PK transaction_id
  • FK from_account_id
  • FK to_account_id
  • amount, type, status, memo

banks 은행

  • PK bank_id
  • bank_name
  • bank_code

promotions 예금 상품

  • PK promotions_id
  • FK bank_id
  • promotion_name, rate
  • term_months, start_date, end_date

history view 조회

  • 최근 5건 거래 내역
  • 상대 계좌·상대 이름 JOIN
  • 취소 가능 시간 계산
  • 상태별 표시

Project Flow

사용자가 돈을 움직이는 순간까지의 흐름

회원 인증

회원가입 후 SHA-256 해시 비밀번호로 로그인하고, role에 따라 사용자와 관리자 화면을 분기합니다.

계좌 생성

은행 코드를 기준으로 날짜와 난수를 조합해 중복 없는 계좌번호를 생성합니다.

송금 실행

잔액, 수취 계좌, 자기 계좌 송금 여부를 검증한 뒤 DB 트랜잭션으로 출금과 입금을 묶습니다.

거래 기록

이체 정보와 상태를 transactions에 저장하고 최근 내역에서 상대 계좌와 이름을 함께 보여줍니다.

1분 취소

PENDING 상태의 거래는 60초 안에 취소할 수 있고, 취소 시 잔액을 반대로 되돌립니다.

Function Set

사용자 기능과 관리자 기능을 하나의 시스템 안에서 연결

사용자 화면

내 계좌 목록 조회, 새 계좌 개설, 계좌 해지

수취 계좌 검증 후 이체, 최근 거래 내역 확인

이체 후 60초 카운트다운 기반 취소 처리

예금 상품 목록 조회와 상품 가입 계좌 생성

관리자 화면

전체 회원 조회와 ACTIVE/BLOCKED 상태 변경

예금 상품 등록, 삭제, 상품별 가입자 조회

총 회원 수, 활성·차단 회원 수, 총 예치 자산 집계

일별 거래 건수와 금액을 테이블·그래프로 전환 표시

Strengths

특장점: 단순 CRUD를 넘어 실제 송금 서비스의 조건을 다룸

60초

이체 직후 취소 가능 시간을 두어 사용자의 실수 대응 시나리오까지 구현했습니다.

트랜잭션 기반 잔액 처리 출금, 입금, 거래 기록 저장을 하나의 작업 단위로 묶어 중간 실패 시 롤백합니다.
권한별 화면 분리 일반 사용자는 금융 기능에 집중하고, 관리자는 회원·상품·통계를 관리합니다.
계좌번호 자동 생성 은행 코드와 날짜 기반 번호를 생성하고 DB 중복 여부를 확인합니다.
운영 관점 통계 회원 상태, 총 예치 자산, 일별 거래 트렌드를 관리자 대시보드에서 확인합니다.

Retrospective

회고 작성 공간

아래 문장은 예시입니다. 실제 발표 전 팀원별 경험과 배운 점으로 교체하면 됩니다.

잘한 점

예시: 기능을 사용자 흐름 기준으로 나눠 구현해서 로그인부터 송금까지 자연스럽게 연결할 수 있었다.

어려웠던 점

예시: DB 테이블명과 컬럼명을 맞추는 과정에서 DAO, 모델, SQL 간 일관성을 계속 확인해야 했다.

개선하고 싶은 점

예시: 다음에는 테스트 데이터와 예외 케이스를 더 체계적으로 준비해 안정성을 높이고 싶다.

Closing
